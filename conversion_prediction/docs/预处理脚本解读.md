# 预处理脚本（preprocessing.py）解读与发现

> 对象：`conversion_prediction/src/conversion_prediction/preprocessing.py`
> 生成日期：2026-08-16
> 配套阅读：`数据探索报告.md`（原始数据的字段与分布）、`../README.md`（项目目标与实验设计）

---

## 一、一句话概述

`preprocessing.py` 把原始行为日志（680 万行、一行一次事件）加工成**无标签泄漏的 session 序列样本**：按 session 聚合、截断订单前缀、哈希编码、计算时间节奏、按时间切分，产出 `session_samples.parquet` + `metadata.json` + `event_lookup.csv`。整个加工完全用 DuckDB 的 SQL 完成，不经过 pandas 内存。

**输入**：`data/raw/view_data.parquet`（一行 = 一次 PV / MC / ORDER 事件）
**输出**：`data/processed/session_samples.parquet`（一行 = 一条 session，列是整数 list）+ 元数据 + event 反查表

---

## 二、数据流全景

```
原始行为日志 (680万行, 一行一事件, 字符串特征)
        │
        │ ① 按 session 分组, 行→序列          (sessions CTE)
        │ ② 字符串→整数ID (hash)             (tokens CTE)
        │ ③ 打 label + 删 ORDER 防泄漏       (marked/prefixes CTE)
        ▼
session_samples.parquet (每行 = 一条 session, 列是整数 list + label + split)
        │
        │ ④ 截断/补零 → 定长 + mask          (dataset.py: collate)
        ▼
batch = { event_ids: [B,S]整数, mask, positions, label }
        │
        │ ⑤ 整数 → Embedding向量 → Transformer (models.py)
        ▼
输出: 这条 session 会下单的概率 (0~1)
```

Transformer 最终要的输入是「**对齐后的整数序列 + mask + label**」。原始数据和它之间隔着四个缺口，预处理填补其中三个（聚合、编码、打标签+防泄漏），定长对齐由 `dataset.py` 完成。

## 三、核心机制详解

### 3.1 特征哈希 `_hash_id`

```python
def _hash_id(expression: str, buckets: int, missing: str | None = None) -> str:
    hashed = f"CAST(1 + hash({expression}) % {buckets} AS INTEGER)"
    return f"CASE WHEN {missing} THEN 0 ELSE {hashed} END" if missing else hashed
```

**关键点：它不返回数字，而是返回一段 DuckDB SQL 字符串**，嵌入大查询里执行。`hash()`、`%`、`CAST` 都是 DuckDB 函数。

映射规则：`字符串 → hash() 得 64 位整数 → % bucket 得 0..bucket-1 → +1 得 1..bucket`。`0` 统一留给「缺失 / padding」，下游 `nn.Embedding(bucket+1, hidden, padding_idx=0)` 正好用索引 0 当 padding 向量。

**这是 feature hashing（哈希技巧）**：用「碰撞换参数可控」。价值 = 无状态、免建词表、天然处理未知值、参数量有硬上限。代价 = 不同值可能撞进同一桶。

四个特征的桶数与真实基数：

| 特征 | 桶数 | 真实基数 | 关系 |
|---|---|---|---|
| event | 4096 | ~679（event_name 678 × 大类） | 桶 > 基数，基本唯一 |
| page | 2048 | 486 | 桶 > 基数，约 57 对碰撞 |
| category | 1024 | 27 | 桶 > 基数，富余 |
| poi | 65536 | 远大于 65536（商家 ID） | 桶 << 基数，硬压缩 |

**参数量 = 桶数 × hidden_dim(64)**。poi 一个特征 4,194,304 参数，占全部 embedding（约 466 万）的 90%，是绝对大头。

### 3.2 `event_type:event_name` token

```python
event_label = "concat(coalesce(event_type, '<NULL>'), ':', coalesce(event_name, '<NONE>'))"
```

把「事件大类 + 具体埋点」压成一个 token，`coalesce` 兜底 NULL。但要注意两点：

1. **ORDER 已在前面的 `prefixes` CTE 删除**，所以 token 空间里只有 PV 和 MC 两类，`ORDER:_order` 永不出现。
2. **所有 PV 事件都塌缩成同一个 token `PV:<NONE>`**（PV 无埋点，event_name 为 NULL），PV 之间的差异（在哪个页面）由 `page_id` 单独承载。

**冗余点（值得注意）**：`event_type` 已被单独编码成 `event_type_id`（`models.py` 有独立 `nn.Embedding(4)`），且 `_mc` 后缀"几乎"能反推大类。所以 `MC:` 前缀对所有真实 token 都是常量，不带来区分度——属于防御性/自解释优先的写法，非必需。更干净的做法是只 hash `event_name` + 靠独立 `event_type_id` 提供大类。

### 3.3 消费阶段识别（stage）

人工写死的关键词规则（非学习），把每个事件归入三个阶段：

| ID | 阶段 | 含义 |
|---|---|---|
| 1 | 需求探索 | 随便逛 |
| 2 | 商户发现 | 找商家 / 看商家卡片 |
| 3 | 消费决策 | 看详情、领券、付款、提交订单 |

把 4 个字段拼成文本 `lower(concat_ws(' ', event_name, page_name, classification_name, first_cate_name))`，用中英文关键词匹配：

- `decision_pattern`（决策）：`coupon/pay/checkout/submit/deal/package/review/address/business.hour/detail/优惠/券/支付/提交订单/套餐/评价/地址/营业/详情`
- `discovery_pattern`（发现）：`poi/merchant/shop/store/list/card/商家/门店/列表/卡片`

CASE 按优先级判断（先命中谁算谁）：

```
1. 文本命中 decision 词     → 3 (决策)
2. 否则 event_type = 'MC'   → 2 (商户发现)
3. 否则文本命中 discovery 词 → 2 (商户发现)
4. 否则                     → 1 (探索)
```

「未命中时 PV 为探索、MC 为商户发现」即指 2 和 4 两条兜底。这是人工注入的领域先验，存在词表覆盖不到的误判；它的存在是为了验证「消费阶段先验是否有效」这一实验假设（见 README）。

### 3.4 时间间隔（time_gap）

`with_gaps` CTE 用 `LAG` 算相邻事件时间差 `gap_ms`（毫秒），再分 6 档：

| time_gap_id | 含义 |
|---|---|
| 1 | 序列起点（首个事件，无前置） |
| 2 | 0–1 分钟 |
| 3 | 1–5 分钟 |
| 4 | 5–30 分钟 |
| 5 | 30 分钟–2 小时 |
| 6 | 2 小时以上 |

阈值：`60000 / 300000 / 1800000 / 7200000` 毫秒。

## 四、完整 SQL（原样保留）

> 以下 SQL 直接摘自源码，`{...}` 为 Python f-string 占位符，运行时被替换为对应表达式/数值。

### 4.1 主查询（事件流 → session 样本）

```sql
WITH raw AS (
  SELECT
    CAST(session_id AS VARCHAR) AS session_id,
    CAST(user_id AS VARCHAR) AS user_id,
    CAST(event_timestamp AS BIGINT) AS event_timestamp,
    event_type, event_name, page_name, classification_name, first_cate_name, poi_id
  FROM read_parquet({_literal(raw_path)})
  WHERE session_id IS NOT NULL AND event_timestamp IS NOT NULL
  {limit_sql}
), marked AS (
  -- 在删除 ORDER 前先生成 session 标签和首个订单时刻。
  SELECT *,
    MAX(CASE WHEN event_type = 'ORDER' THEN 1 ELSE 0 END)
      OVER (PARTITION BY session_id) AS label,
    MIN(CASE WHEN event_type = 'ORDER' THEN event_timestamp END)
      OVER (PARTITION BY session_id) AS first_order_timestamp
  FROM raw
), prefixes AS (
  -- 正样本只保留首个订单前的行为，防止模型直接看到答案。
  SELECT * FROM marked
  WHERE event_type <> 'ORDER'
    AND (label = 0 OR event_timestamp < first_order_timestamp)
), with_gaps AS (
  -- 相邻行为时间差刻画用户决策节奏。
  SELECT *,
    event_timestamp - LAG(event_timestamp) OVER (
      PARTITION BY session_id ORDER BY event_timestamp, event_type, event_name
    ) AS gap_ms
  FROM prefixes
), tokens AS (
  -- 将类别字段、消费阶段和时间间隔转换为 Embedding ID。
  SELECT *,
    {event_id} AS event_id,
    CASE event_type WHEN 'PV' THEN 1 WHEN 'MC' THEN 2 ELSE 3 END AS event_type_id,
    {page_id} AS page_id,
    {category_id} AS category_id,
    {poi_id} AS poi_id_hash,
    {stage_id} AS stage_id,
    CASE
      WHEN gap_ms IS NULL THEN 1
      WHEN gap_ms <= 60000 THEN 2
      WHEN gap_ms <= 300000 THEN 3
      WHEN gap_ms <= 1800000 THEN 4
      WHEN gap_ms <= 7200000 THEN 5
      ELSE 6
    END AS time_gap_id
  FROM with_gaps
), sessions AS (
  -- 按时间顺序把逐行事件聚合为一个变长 session 样本。
  SELECT
    session_id,
    any_value(user_id) AS user_id,
    MIN(event_timestamp) AS session_start,
    MAX(label)::INTEGER AS label,
    COUNT(*)::INTEGER AS sequence_length,
    list(event_id ORDER BY event_timestamp, event_type, event_name) AS event_ids,
    list(event_type_id ORDER BY event_timestamp, event_type, event_name) AS event_type_ids,
    list(page_id ORDER BY event_timestamp, event_type, event_name) AS page_ids,
    list(category_id ORDER BY event_timestamp, event_type, event_name) AS category_ids,
    list(poi_id_hash ORDER BY event_timestamp, event_type, event_name) AS poi_ids,
    list(stage_id ORDER BY event_timestamp, event_type, event_name) AS stage_ids,
    list(time_gap_id ORDER BY event_timestamp, event_type, event_name) AS time_gap_ids
  FROM tokens
  GROUP BY session_id
  HAVING COUNT(*) >= {int(data_cfg['min_seq_len'])}
), ordered AS (
  -- 按 session 起始时间切分，模拟用过去数据预测未来数据。
  SELECT *,
    ROW_NUMBER() OVER (ORDER BY session_start, session_id) AS split_row,
    COUNT(*) OVER () AS total_sessions
  FROM sessions
)
SELECT * EXCLUDE (split_row, total_sessions),
  CASE
    WHEN split_row <= total_sessions * {train_ratio} THEN 'train'
    WHEN split_row <= total_sessions * {train_ratio + val_ratio} THEN 'validation'
    ELSE 'test'
  END AS split
FROM ordered
```

**占位符解析**（以 `configs/base.yaml` 为例）：

| 占位符 | 展开结果 |
|---|---|
| `{_literal(raw_path)}` | `'data/raw/view_data.parquet'`（路径转义成字符串字面量） |
| `{limit_sql}` | `LIMIT n`（`row_limit` 非空时）或空串 |
| `{event_id}` | `CAST(1 + hash(concat(coalesce(event_type, '<NULL>'), ':', coalesce(event_name, '<NONE>'))) % 4096 AS INTEGER)` |
| `{page_id}` | `CASE WHEN page_name IS NULL THEN 0 ELSE CAST(1 + hash(page_name) % 2048 AS INTEGER) END` |
| `{category_id}` | `CASE WHEN first_cate_name IS NULL THEN 0 ELSE CAST(1 + hash(first_cate_name) % 1024 AS INTEGER) END` |
| `{poi_id}` | `CASE WHEN poi_id IS NULL THEN 0 ELSE CAST(1 + hash(CAST(poi_id AS VARCHAR)) % 65536 AS INTEGER) END` |
| `{stage_id}` | 见 3.3 的 CASE 表达式 |
| `{train_ratio}` / `{val_ratio}` | `0.70` / `0.15` |
| `{int(data_cfg['min_seq_len'])}` | `2` |

7 个 CTE 的职责：`raw` 读原始日志 → `marked` 打标签 → `prefixes` 删订单防泄漏 → `with_gaps` 算时间差 → `tokens` 编码成 ID → `sessions` 聚合变 list → `ordered` 按时间排序编号 → 最终 SELECT 切 train/val/test。

### 4.2 样本分布统计 SQL（写 metadata.json）

```sql
SELECT split, COUNT(*) AS sessions, SUM(label) AS positives,
       AVG(label) AS positive_rate, AVG(sequence_length) AS mean_length,
       quantile_cont(sequence_length, 0.95) AS p95_length
FROM read_parquet({_literal(output_path)}) GROUP BY split ORDER BY split
```

### 4.3 event 反查表 SQL（写 event_lookup.csv）

```sql
WITH counts AS (
  SELECT {event_id} AS event_id, {event_label} AS event_label, COUNT(*) AS frequency
  FROM (
    SELECT event_type, event_name
    FROM read_parquet({_literal(raw_path)})
    {limit_sql}
  ) AS lookup_source
  WHERE event_type <> 'ORDER'
  GROUP BY event_id, event_label
), ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY event_id ORDER BY frequency DESC) AS rank
  FROM counts
) SELECT event_id, event_label, frequency FROM ranked WHERE rank = 1 ORDER BY event_id
```

用途：哈希可能碰撞，解释时为每个 `event_id` 保留出现频率最高的原始名称。

## 六、需要注意的点 / 发现清单

1. **标签防泄漏**：`label` 和 `first_order_timestamp` 在删 ORDER **之前**用窗口函数算好（`marked`），之后 `prefixes` 删 ORDER 并把正样本截到订单前。ORDER token 永不进序列。
2. **时间切分而非随机切分**：按 `session_start` 排序后 70/15/15 切分，模拟「用过去预测未来」，避免随机切分造成未来信息泄漏。
3. **`page_name` 用 hash 是净损失**：486 个稳定小基数值用 2048 桶，白白撞约 57 对；更优做法是用真词表 1:1 编码（0 碰撞、表更小）。纯 hash 是图统一，牺牲了 page 的精度。
4. **`event_type` 前缀冗余**：`MC:` 对所有真实 token 都是常量，且 `event_type_id` 已单独编码了大类；前缀主要带来可解释性（反查时 `MC:资源卡片_mc` 更自解释）。
5. **所有 PV 塌缩成 `PV:<NONE>`**：PV 之间差异靠 `page_id` 承载，event token 实际只负责区分 MC 的几百种点击动作。
6. **`poi_id` 是硬压缩**：65536 桶 << 真实商家数，必然大量碰撞；但长尾商家共享桶反而学得更稳，是「参数可控 vs 区分度」的折中。
7. **hash 值依赖 DuckDB 版本**：`hash()` 算法跨版本可能变化，同一次训练/推理用同一环境即可，不必跨版本比对具体数值。
8. **`classification_name` 只被间接用**：仅参与 `stage` 的关键词推导（27 类高质量现成特征），未作为独立 embedding——是潜在可挖的特征。
9. **`stage` 是人工先验**：词表硬编码，覆盖不到会误判；存在是为验证「阶段先验是否有效」这一实验假设。
10. **连续特征未接入**：`page_stay_time`（停留时长）是连续值，走不了 hash→embedding 路径，需单独离散化或投影，当前完全未用。

## 七、当前被排除的特征（改进候选）

`raw` CTE 只选了 9 列，以下字段未参与建模（搜索确认：`page_stay_time`/`device_type`/`page_city_name` 在 src 中零出现，`second/third_cate` 仅 EDA 用，`user_id` 仅计数用）：

| 字段 | 类型 | 排除原因 | 接入难度 | 预估价值 |
|---|---|---|---|---|
| `page_stay_time` | 连续 | 走不了 hash 路径 + 不在实验假设内 | 中（需离散化或连续投影） | 高（停留久=强下单信号） |
| `classification_name` | 类别(27) | 仅间接用于 stage | 低 | 高（干净现成特征） |
| `device_type` | 类别(4) | 弱信号 + 不在假设内 | 低 | 低 |
| `page_city_name` | 类别 | 同上 | 低 | 中 |
| `second_cate_name`/`third_cate_name` | 类别 | 缺失率高、长尾 | 中 | 低-中 |
| `user_id` | 身份 | **正确地排除**——会记住个体、无法泛化新用户 | — | 负（不应加） |

> 关键结论：这些字段不是「留到后面用」，而是当前实验明确划在范围外。项目目标是「用干净的消融链验证序列建模/消费阶段/时间间隔三个假设」（见 README），不是「堆所有特征刷最高分」。`page_stay_time`、`classification_name` 属于**未来值得加、且大概率有效的改进项**，前提是当前实验链跑通后再单独做消融。
