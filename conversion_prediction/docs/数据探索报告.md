## 五、核心发现

### 5.1 数据性质

- 一行 = 一次事件，而非一个 session；同一个 `session_id` 下有多条事件（采样内平均约 14 条/会话）。
- `event_type` 全量分布（6,807,745 行）：

| 事件类型 | 行数 | 占比 | 含义 |
|---------|------|------|------|
| PV | 4,711,099 | 69.2% | 页面浏览 |
| MC | 1,853,592 | 27.2% | 点击（埋点） |
| ORDER | 243,054 | **3.57%** | 下单（= 转化正样本） |

### 5.2 `event_timestamp` 与 `stat_time` 是同一个时刻的两种表示

- 20 万行抽样对比，**0 行不一致**，完全冗余。
- `event_timestamp`：毫秒级 Unix epoch（数字），**保留毫秒精度**。
- `stat_time`：转成北京时间后**截断到秒**的字符串。
- **结论**：做时间差特征必须用 `event_timestamp`，它可直接相减且精度更高。

### 5.3 `page_stay_time` 单位是毫秒，不是秒

- 中位数 5308、均值 13854、最大值 1.3M。
- 按「秒」理解中位数 88 分钟显然不合理；按「毫秒」理解中位数 5.3 秒、最大值 21 分钟，符合直觉。

### 5.4 转化信号 = 下单事件

下单可以从三个字段交叉确认，三者高度一致：

| 信号来源 | 取值 |
|---------|------|
| `event_type` | `ORDER` |
| `classification_name` | `BO事件`（234,844 次） |
| `event_name` | `_order` / `mrn_order` / `拼好饭下单事件` / `购物车下单` 等约 20 种 |

**建议**：定义 label 时用 `event_type == "ORDER"` 最直接，或按 `classification_name == "BO事件"` 更稳。

### 5.5 `page_name` 结构（486 种取值，长尾极重）

头部高度集中，前 12 个页面吃掉大部分流量：

```
点菜页(门店)               1,567,196
美食商家详情页_美团         1,086,890
搜索结果列表页(百花园&商品搜)  773,538
到综美团商户详情页           602,403
闪购标准版商家页             521,663
闪购品质版商家页             449,543
外卖首页                   422,982
酒店_商户详情页_双端融合mrn   175,699
提交订单页                  174,914
新评价列表页                173,524
```

486 个页面里绝大多数只出现 1–3 次，是超长尾。

### 5.6 `event_name` 结构（678 种取值）

命名规律清晰：

1. **点击埋点**几乎都以 `_mc` 结尾：`item+element通用_mc`、`资源卡片_mc`、`搜索结果-精确商家列表区_mc`……
2. **下单事件**不含 `_mc`，而含 `_order` / `下单` / `订单` / `提交订单`：

```
_order             178,311
mrn_order           41,138
拼好饭下单事件        12,438
购物车下单            3,686
到餐交易平台-啡快订单    2,068
门票下单               745
用户下单               117
```

**注意**：下单事件散落在几十种 `event_name` 里（外卖 / 团购 / 门票 / 酒店…），不能只认 `_order` 一个词。

### 5.7 `classification_name` 是从 page/event 派生的标准化分类（27 种）

派生规则取决于事件类型：

| 事件类型 | 从哪派生 | 说明 |
|---------|---------|------|
| PV | `page_name` | 归类成页面类型（详情页 / 列表页 / 信息页…） |
| MC | `event_name` | 归类成动作类型（卡片 / 各按钮…） |
| ORDER | — | 统一归为 `BO事件` |

**归并力度**：

| classification_name | 覆盖原始取值数 | 例子 |
|---|---|---|
| 商家详情页 | 29 个 page_name | 点菜页、美食商家详情页、闪购商家页… |
| 商家卡片 | 298 个 event_name | item+element通用_mc、资源卡片_mc… |
| 打电话给商家按钮 | 63 个 event_name | 电话_click_mc、电话模块_电话点击_mc… |
| BO事件 | 20 个 event_name | _order、mrn_order、拼好饭下单事件… |

**价值**：`classification_name` 是数据方做好的「用户对商家做了什么」的干净分类，基数极低（27），是质量很高的现成特征。但要注意——**它覆盖的都是跟「商家」相关的交互**，纯逛频道页、首页等非商家浏览该字段为 `(空)`。

### 5.8 业务线没有独立字段，隐含在别处

- 表里**没有**「业务线」这一列。
- 业务线只隐含在：
  - `page_name`：靠关键词猜（含「酒店」→酒店线、含「医药/买药」→医药线、含「闪购」→闪购线……），但没有统一规范。
  - `page_id` 前缀：**基本靠不住**——98% 的 `page_id` 都是不透明的 `c` 前缀，只有极少数有含义（`meishiHome`=美食、`hotel`=酒店、`travel`=度假、`paotui`=跑腿）。
- **要加业务线特征，正确做法是用 `page_name` 写关键词规则派生一列。**

### 5.9 `page_id` 与 `page_name` 一一对应

- 采样内 251 个 `page_id` ↔ 240 个 `page_name`，无一对多。
- 说明 `page_id` 是稳定的页面 ID，可直接哈希（配置里 `page: 2048` 即此用途）。

### 5.12 session 结构与下单次数分布

**session 是什么**：`session_id` 是「UUID + 起始时间戳(毫秒)」拼接的字符串，同一个 `session_id` 下的所有事件算作一次用户连续使用过程。在本项目中，**一个 session = 一个训练样本**（事件序列 + 二分类 label）。

| 指标 | 值 |
|------|-----|
| 总 session 数 | 496,872 |
| 每个 session 事件数 | 最少 2，中位数 10，最多 159 |

**一个 session 可以有多次下单**（全量统计，按 session 分组后的下单次数）：

| 下单次数 | session 数 | 占比 |
|---------|-----------|------|
| 0 次 | 319,262 | 64.3% |
| 1 次 | 127,992 | 25.8% |
| 2 次 | 38,406 | 7.7% |
| 3 次 | 8,169 | 1.6% |
| 4 次 | 2,058 | 0.4% |
| 5 次 | 628 | 0.13% |
| 6~12 次 | 357 | <0.1% |

关键数字：

- **下单 ≥ 2 次的 session 有 49,618 个，约占总 session 的 10%**；极端情况一个 session 下 12 单。
- **转化率（session 级）= 35.7%**：至少下 1 单的 session 共 177,610 个。⚠️ 注意与 5.1 里「ORDER 事件占 3.57%」是**两个口径**——前者是"会话转化率"，后者是"事件占比"，别混淆。
- **ORDER 事件数 ≠ 转化 session 数**：全量 243,054 个 ORDER 事件 / 177,610 个转化 session ≈ **平均每个转化 session 下 1.37 单**。

## 六、对转化预测项目的启示与建议

1. **label 定义**：优先用 `event_type == "ORDER"` 或 `classification_name == "BO事件"` 判定 session 是否转化；下单事件在 `event_name` 里散落多类，别只认单一关键词。
2. **时间特征**：`time_gap` 之类的时间差用 `event_timestamp`（毫秒、可相减），不要用 `stat_time`。
3. **停留时长**：`page_stay_time` 单位是毫秒，做特征前先确认量纲（必要时 `/1000`）。
4. **分类特征**：`classification_name`（27 类）是现成的高质量特征，比原始 `page_name`（486）/ `event_name`（678）干净得多；`page_id` 与 `page_name` 一一对应，哈希时二选一即可。
5. **业务线**：表中无此字段，如需使用需从 `page_name` 写规则派生。
6. **配置核对**：`configs/base.yaml` 里 `hash_buckets.category: 1024` 需确认填的是 `classification_name`（动作分类）还是 `first_cate_name`（商家品类）——二者语义完全不同。
7. **label 是否需要区分下单次数**：若只做二分类（转化/未转化），多个 ORDER 都归为 label=1 即可；但 28% 的转化 session 有 ≥2 次下单，若关心复购/客单价，需把目标改成回归或多分类，而非简单二值化。
